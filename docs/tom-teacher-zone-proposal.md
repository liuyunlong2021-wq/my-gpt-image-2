# Tom 老师专区：存储与发布方案

状态：待审核。本文件对比两种实现路径，供管理员和内容维护者确认后进入开发。当前站点保持纯静态 HTML、CSS、原生 JavaScript；本提案不创建云资源、不改生产页面、不部署。

## 目标与约束

- 首页“创作参考”区域增加 Tom 老师专区入口，公开展示作品图片、视频、简介和可复制提示词。
- Tom 老师可以每天更新；访客无需登录即可浏览。
- 尽量沿用 GitHub PR 审核和 Cloudflare Pages 静态部署。
- 图片、视频都是公开展示内容，不在浏览器中收集用户上传。
- 首版不建设账号系统、管理后台、数据库、服务端上传 API、转码流水线。

## 方案一：媒体文件和内容清单都提交 Git

### 设计

图片、视频以及作品元信息一并放进仓库。前端读取 `data/tom-teacher.json`，媒体用相对路径引用，例如 `media/tom/2026/11/作品ID/cover.webp`。合并到生产分支后，由 Cloudflare Pages 发布静态文件。

建议目录：

```text
data/tom-teacher.json
media/tom/2026/11/作品ID/cover.webp
media/tom/2026/11/作品ID/image-01.webp
media/tom/2026/11/作品ID/video.mp4
```

内容记录沿用方案二的数据结构，只把媒体 URL 改为相对路径。视频需要统一编码为浏览器普遍支持的 H.264/AAC MP4；图片建议转为 WebP/AVIF 并控制尺寸。提交前通过脚本检查 JSON、文件存在、扩展名、单文件大小和重复 ID。

### 更新与发布流程

1. Tom 老师整理作品媒体并按约定格式压缩、命名。
2. 将媒体和 `data/tom-teacher.json` 一起提交到 Git 分支。
3. 创建 PR；检查文案、资源路径、图片显示和视频播放。
4. PR 预览通过后由有权限的维护者合并，Cloudflare Pages 发布。
5. 撤下作品时从 JSON 移除记录并在同一 PR 删除对应媒体文件。

### 开发实现清单

- 新增 `data/tom-teacher.json` 和媒体目录规范/示例记录。
- 首页“创作参考”增加专区入口；按现有 UI 规范实现作品列表、详情查看、图片/视频展示和复制提示词。
- 媒体延迟加载；视频只在详情打开后加载，列表仅显示封面。
- 新增内容校验脚本，校验字段、唯一 ID、媒体路径存在、文件格式和体积上限；在 PR 工作流运行。
- 配置并验证 Cloudflare Pages PR 预览及合并后的自动发布，确保 Pages 输出目录包含 `media/`。
- 定义文件大小、单作品媒体数、视频时长和仓库累计体积上限；超限素材拒绝入库。

### 优点

- 不需要新增对象存储、域名、访问密钥或上传权限配置。
- 媒体与清单在同一个 PR 审核、回滚、备份，追溯关系简单。
- PR 预览和静态托管路径直接，发布链路容易理解。
- 没有运行时后端，日常运行架构最简单。

### 缺点与风险

- 图片和视频进入 Git 历史后，普通删除不会缩小仓库历史；大视频会快速增加 clone、备份和 CI 成本。
- GitHub 单文件限制为 100 MiB；即使低于该限制，大型媒体也不适合频繁放入 Git。Git LFS 会增加配置与存储/流量配额管理，不建议作为首版默认方案。
- Pages 每次发布需要上传站点资产；媒体增长会拖慢构建/部署和预览。
- 替换素材会增加新的二进制版本，旧版本仍保留在 Git 历史中。
- 压缩转码和审核素材质量主要依赖人工；视频格式不统一会导致播放失败或流量浪费。

### 适用情况

适合先做小规模试点：作品少、更新量低、媒体很小，且团队希望零云资源配置。需要在开发前定量确认仓库体积预算和视频限制。

## 方案二：媒体放 Cloudflare R2，内容清单进 Git（推荐）

### 设计

图片和视频存放在独立 R2 bucket 或专用前缀，使用只读公开媒体域名；作品元信息保存在 `data/tom-teacher.json`。前端仍是纯静态站点，不需要应用后端或数据库。Tom 老师上传对象后，通过 GitHub PR 提交清单，审核合并后发布。

建议对象路径使用不可变 ID，避免 CDN 缓存导致替换旧文件后页面仍显示旧内容：

```text
tom/2026/11/作品ID/cover.webp
tom/2026/11/作品ID/image-01.webp
tom/2026/11/作品ID/video.mp4
```

内容记录示例：

```json
{
  "id": "tom-2026-11-04-001",
  "title": "作品标题",
  "description": "作品简介",
  "prompt": "可复制的提示词",
  "cover": "https://media.dazi.studio/tom/2026/11/作品ID/cover.webp",
  "media": [
    {
      "type": "video",
      "url": "https://media.dazi.studio/tom/2026/11/作品ID/video.mp4",
      "alt": "作品视频"
    }
  ],
  "tags": ["示例"],
  "publishedAt": "2026-11-04T08:00:00+08:00"
}
```

### 更新与发布流程

1. Tom 老师通过 R2 控制台或管理员提供的受限上传方式上传图片/视频。
2. 将公开媒体 URL、标题、提示词等信息新增到 `data/tom-teacher.json`。
3. 创建 PR；自动检查 JSON 字段、ID、允许的媒体域名和资源可访问性，并查看 Pages 预览。
4. 审核通过后合并；Cloudflare Pages 发布清单和前端页面，R2 媒体无需随部署重复上传。
5. 撤下作品时先从清单移除并发布；对象可按保留策略归档或删除。删除对象前确认没有其他页面引用。

### 开发实现清单

- 新增 `data/tom-teacher.json`，定义字段 schema 和内容校验脚本。
- 新增专区入口、作品列表/详情、图片和视频预览、复制提示词；支持手机端和空数据/加载失败状态。
- 媒体仅在需要时加载；视频使用原生 `<video controls playsinline preload="none">`，封面图片懒加载。
- 校验媒体 URL 必须使用配置的媒体域名；PR 校验只检查公开 HEAD/GET 可访问性，不要求 R2 写凭据。
- 配置 R2 bucket/前缀、公开读取域名、内容类型和缓存规则；上传写权限单独发放，网站前端不得包含写密钥。
- 配置 GitHub PR 预览和合并后的 Pages 自动发布；验证 R2 CORS（仅当浏览器跨域读取资源需要时）以及视频 Range 请求/播放。
- 定义媒体大小、格式、时长、数量、保留与撤下规则，并监控存储和出站流量费用。

### 优点

- Git 仓库只保存小型 JSON 清单，媒体增长不会膨胀 Git 历史。
- R2 对象可单独上传和管理；发布清单时不必重新推送大文件。
- 适合每天持续增加图片和视频，媒体域名、缓存和对象生命周期可独立管理。
- PR 仍负责内容审核和发布，前端继续保持静态，不需要运行时后端。

### 缺点与风险

- 需要管理员配置 bucket、公开域名、DNS/证书、缓存和访问策略；托管、流量及相关服务条款需要管理员确认。
- 上传与更新涉及两个位置（R2 和 Git PR）；上传后未合并的媒体会成为孤儿对象，需要清理规则。
- 媒体 URL 公开可访问；清单移除不等于对象立即不可访问，撤下流程必须包含对象处置。
- 若使用 CDN 长缓存，覆盖同一路径会出现旧缓存；应使用不可变路径或版本号。
- R2 与 Pages 资源发布不是同一事务，需要先上传媒体再合并清单；PR 校验和预览负责发现失效链接。

### 适用情况

适合持续日更、视频较多或作品长期增长的公开专区。整体仍无应用后端；只有媒体存储和交付由 Cloudflare 托管。

## 对比与建议

| 维度 | 方案一：媒体进 Git | 方案二：媒体进 R2、清单进 Git |
|---|---|---|
| 应用后端 | 不需要 | 不需要 |
| 管理员首次配置 | 最少 | 需要 R2、媒体域名和权限配置 |
| 每日发布 | 一个 PR 包含全部文件 | 上传媒体，再提交清单 PR |
| 仓库增长 | 随媒体累计，删除也保留历史 | 仅清单增长 |
| 视频规模适应性 | 较差，需严格限额 | 较好，仍需设置流量和存储预算 |
| 发布审查/回滚 | Git 内可整体追溯 | 清单可追溯；媒体需按对象策略处理 |
| 日常运维 | 仓库和部署体积管理 | 对象生命周期、缓存和孤儿对象管理 |

**建议选择方案二**：用户已明确这是每日更新并公开展示的内容，图片/视频持续进入 Git 会让仓库历史和部署资产不断变大。方案二不需要开发后端，保留 Git PR 审核，同时把大文件放到适合媒体的对象存储。若管理员暂时无法提供 R2 资源，可先按方案一做小规模试点，并设置严格的单文件及累计体积门槛。

## 需要管理员配合的材料与操作

### 方案一所需

- 确认媒体可以公开纳入 Git 仓库和仓库备份。
- 确认单文件、单作品、月新增及仓库累计体积预算；默认建议禁止超过 50 MiB 的单文件，视频先限制时长/码率。
- 确认 Tom 老师的 GitHub 账号及其是否可创建 PR；合并权限仍由维护者持有。
- 确认 Cloudflare Pages 的 PR 预览和合并自动部署已启用，以及 Pages 输出目录设置。

### 方案二所需

- 提供或创建专用 Cloudflare R2 bucket（也可由管理员指定隔离前缀），告知 bucket 名称和所在 Cloudflare 账号/项目。
- 配置媒体公开读取域名，例如 `media.dazi.studio`，并确认 DNS、TLS、公开访问和缓存规则由谁维护。
- 创建仅限指定 bucket/前缀的上传身份或控制台账号，限定 Tom 老师和维护者；写密钥应通过安全渠道交付，不能写入仓库、PR、网页代码或聊天记录。
- 确认是否采用 R2 自定义域名直接读取；若前端方式需要跨域访问，再提供允许的 CORS origin（至少 `https://dazi.studio`，另加 Pages 预览域名策略）。
- 确认存储/出站流量预算、对象保留与删除规则、备份策略及内容下架责任人。
- 确认视频编码要求与单文件大小/时长限制；如需要转码服务，另行提供获批的服务和费用预算。首版不默认建设转码后端。
- 确认 GitHub Actions/Cloudflare Pages PR 预览和生产自动部署所需仓库权限；普通读取校验不应使用 R2 写密钥。

## 两方案共同的验收标准

- 首页入口与专区在桌面和手机端正常展示；支持公开访问，不要求登录。
- 图片、视频、提示词可查看/播放/复制；列表不会预加载全部视频。
- 无效 JSON、重复 ID、错误媒体域或缺失文件会导致 PR 校验失败。
- PR 预览可验证内容，合并后 Pages 发布可正常访问。
- 已发布作品可撤下，且清单状态和媒体对象处置一致。
- 不创建站内上传表单、账号系统、后端 API 或数据库。

## 待管理员/内容方确认

- 选择方案一或方案二（推荐二）。
- 首版是否同时开放图片与视频，以及单作品媒体数量、单文件大小、视频时长限制。
- Tom 老师能否使用 GitHub PR 更新清单；若不能，需另外评估授权发布流程，但不因此默认开放无认证上传接口。
- 详情交互采用独立页面还是弹窗；建议先采用现有首页风格的详情弹窗，避免引入路由。
- Pages PR 预览、生产自动发布的当前配置和负责人。

## 建议实施顺序

1. 管理员确认方案、内容限制和所需资源，并完成对应材料清单。
2. 配置静态托管预览/发布链路；方案二先验证媒体域名读取和视频 Range 播放。
3. 实现清单 schema、校验脚本、Tom 老师专区入口及作品交互。
4. 添加少量授权样例，审查版权归属、移动端体验、缓存、播放和撤下流程。
5. 在 PR 预览验收后，由维护者合并发布；管理员确认线上结果。
